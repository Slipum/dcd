# ТЗ: `dcd` (рабочее название) — GitOps-CD для Docker Compose без Kubernetes

Лицензия: Apache-2.0. Язык: Rust (tokio, bollard, serde). Платформы: Linux amd64, macOS Apple silicon.

## 1. Цель
CLI-утилита, запускаемая **на хосте** (не в Docker), которая приводит запущенные Compose-стеки в соответствие с YAML-политикой и автоматически обновляет сервисы при появлении нового образа в registry.

## 2. Отличие от Watchtower / Diun
- Желаемое состояние (стеки, сервисы, границы версий) описано в Git и YAML-политике.
- Registry — триггер обновления внутри границ политики, а не источник истины.
- Деплой всегда по digest, healthcheck после деплоя, автоматический откат.

## 3. Границы
**v1:** только сервисы Docker Compose; стратегия `recreate`; один хост.
**Позже:** blue-green (только за reverse proxy, без host-портов и stateful-сервисов), голые контейнеры, несколько хостов.
**Не цель:** оркестрация, Kubernetes, веб-интерфейс.

## 4. Функциональные требования
| ID | Требование |
|----|-----------|
| FR-01 | Политика в YAML, валидация (`validate`), JSON Schema для IDE |
| FR-02 | Источники: Git-репозиторий (compose + политика) и registry-триггер |
| FR-03 | Приоритет: Git задаёт границы (тег/semver/digest), registry только сообщает о новых образах внутри границ |
| FR-04 | Registry: Docker Hub, GHCR, Gitea, Forgejo (единый клиент OCI Distribution, разная авторизация) |
| FR-05 | Определение изменений по digest манифеста **для платформы хоста**, не по digest индекса |
| FR-06 | Триггеры: опрос по интервалу и вебхук (HMAC, по умолчанию localhost) |
| FR-07 | Обновление Compose через `docker compose` CLI; деплой с pin по digest через сгенерированный override-файл |
| FR-08 | Стратегия `recreate`; поле `strategy` зарезервировано под `blue_green` |
| FR-09 | Настройка ресурсов: `volumes`/`networks` — `keep` или `recreate`; `external` сети не трогаются никогда |
| FR-10 | Healthcheck: из образа по умолчанию, свой в политике приоритетнее, `none` — откат и blue-green недоступны |
| FR-11 | Автооткат при провале healthcheck на предыдущий digest |
| FR-12 | Ручное подтверждение: интерактивный prompt (TTY) и команда `approve` |
| FR-13 | Идемпотентность и защита от лишних обновлений (правила — `idempotency.md`) |
| FR-14 | Stateless: предыдущий и применённый digest хранятся в labels контейнера |
| FR-15 | Опциональный файл истории деплоев (журнал, не источник истины) |
| FR-16 | Команды: `init`, `validate`, `check`, `diff`, `apply`, `approve`, `rollback`, `status`, `daemon` |
| FR-17 | Блокировка: не более одного деплоя на стек одновременно |

## 5. Исключено из v1
Проверка подписей образов (cosign), уведомления, окна обслуживания, метрики Prometheus, порядок обновления по зависимостям, сканирование уязвимостей, мультихост. Вернёмся после v1.

## 6. Нефункциональные требования
- NFR-01 Безопасность: доступ к `docker.sock` = root; журнал аудита, секреты только из env/файлов, никогда в логах.
- NFR-02 Надёжность: любой сбой деплоя оставляет сервис в рабочем состоянии (откат) либо явно сообщает, что откат невозможен.
- NFR-03 Идемпотентность: повторный `apply` без изменений делает ноль изменяющих вызовов Docker; проверяется тестами (`idempotency.md`).
- NFR-04 Код: функция ≤ 30 строк, файл ≤ 200 строк (пустые строки и комментарии считаются); файл — один компонент, папка — однотипные компоненты.
- NFR-05 Линт: clippy pedantic, запрет `unwrap`/`expect`/`panic` вне тестов, `forbid(unsafe_code)`; длина файлов проверяется скриптом в pre-commit и CI.
- NFR-06 Тесты: после каждого модуля, по всем классам эквивалентности.
- NFR-07 Сокет Docker: автоопределение (`/var/run/docker.sock`, `~/.docker/run/docker.sock`), переопределяется флагом.

## 7. Ключевые технические решения
1. Деплой через override-файл: `image: repo@sha256:...` + labels `dcd.digest`, `dcd.previous-digest`.
2. «Ожидает подтверждения» — вычисляемое состояние (кандидат ≠ запущенный digest и `approval: manual`), хранить его не нужно.
3. Откат использует локально сохранённый предыдущий образ.
4. Git-кэш лежит в кэш-директории и состоянием не считается.
5. Отвергнутый digest (после отката) запоминается в label `dcd.rejected`, чтобы daemon не повторял неудачный деплой бесконечно.
6. Override-файл и labels детерминированы (без времени и случайных значений), иначе Compose пересоздаст контейнер при каждом запуске.

## 8. Риски
Лишние обновления (меры — `idempotency.md`); rate limits registry (использовать HEAD манифеста); потеря конфигурации при recreate; два экземпляра утилиты одновременно (см. FR-17).
